# DT-34 · La carta muerta del outbox no tiene herramienta

> **Fase:** [Fase 2 — US-03](../Fases/fase-2-us03-recordatorios.md) (origen) · **Feature:** [us03-recordatorios](../Features/us03-recordatorios.md) · **Plan:** [US-03](../US/03-recordatorios.md) · **Relacionado:** [ADR-12](../Decisions/ADR-12.md), [DT-19](../Deudas/DT-19.md)

**Origen:** [ADR-12 §3](../Decisions/ADR-12.md) (prevista 3 del ADR)
**Severidad:** 🟡 baja · **Estado:** abierta — contraída el 2026-10-03 (`f95b637`, rama
`feature/fase2-recordatorios`)

## Qué pasa

Un hecho que falla `EVENTOS_SALIDA_MAX_INTENTOS` veces (10) queda `fallido` en `eventos_salida`, con
`ultimo_error = '<Suscriptor>:<error.name>'`, y sale un log de error con
`alerta = "eventos_salida.fallido"`. No se purga. Para reintentarlo, hoy solo hay SQL a mano:

```sql
UPDATE eventos_salida
   SET estado = 'pendiente', intentos = 0, proximo_intento_en = now(), ultimo_error = NULL
 WHERE id = '<id del hecho>' AND estado = 'fallido';
```

**Para los recordatorios, casi todo se cura solo:** la reconciliación de respaldo (cada hora) reconcilia
las citas vigentes de los próximos 8 días **sin ningún recordatorio para su inicio actual**, y la
política 3 del envío cancela al enviar si la configuración está apagada. Queda un hueco: si muere un
`ConfiguracionRecordatorioActualizada` que **cambió las antelaciones**, las citas que ya tenían
recordatorios siguen con las antelaciones viejas, porque el respaldo no las mira.

## Por qué importa

Quien recibe la alerta necesita saber qué hecho murió, por qué y cómo reintentarlo sin tocar la base a
ciegas. Con un solo suscriptor el volumen es mínimo, pero cada suscriptor nuevo suma motivos de muerte.

## Cómo se cierra

Un comando de soporte (`npm run outbox:reintentar -- <id>` o similar, sin ruta HTTP) que liste los
`fallido` con su código y los devuelva a `pendiente`, más una entrada en el runbook de operación. Como
mínimo, mientras tanto, el SQL de arriba documentado junto a la alerta en Better Stack.
